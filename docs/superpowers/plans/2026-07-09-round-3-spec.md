## 1. Loooop/Lop: "Initialize" clears the loop

Neither module overrides `onReset`, so Ctrl+I resets knobs but the recorded loop keeps playing. Add to both modules:

```cpp
void onReset(const ResetEvent& e) override {
    Module::onReset(e);
    engine.clear();
}
```

`clear()` is already audio-safe (no zero-fill) and already bumps the display cache's waveform revision. Module-level; compile-verified (no headless lane for Rack modules).

## 2. beads grain-scheduler fix bundle (one subsystem, three audible defects)

a. **Grain-kill fallback fade never reaches zero** (`grain.h`): `fade = counter/4` runs 1.0→0.25 then hard-cuts — a 0.25-amplitude step. Change to `(counter − 1)/kFallbackFadeSamples` so the last value is 0.

b. **"Kill the oldest grain" kills an arbitrary one** (`grain_engine.cpp`): the fallback marks the first non-pending grain by array index — frequently the *newest*. Fix by tracking spawn order: a monotonically increasing `uint32_t spawn_serial_` on `GrainEngine`, stamped onto each grain at activation; the kill fallback picks the active grain with the lowest serial. (Exact and cheap; wraparound at 2³² is \~24 hours of continuous 50 Hz grains and self-heals — note it in a comment.)

c. **Scheduler mode-change off-by-one + dead state** (`grain_scheduler.cpp`): reset `gate_phase_` (the clock-division counter) when the trigger mode changes, so the first division after gated→clocked isn't off by one. Delete the dead `clock_period_` measurement/smoothing and the never-read `BeadsParameters::clock_interval_samples` field (no host writes it — verify by grep before deleting).

**Tests:** kill-fade reaches exactly 0 (unit-level on the fade sequence or via a saturated-pool render asserting no step > bound); kill-oldest (saturate the pool, assert the earliest-spawned grain is the one killed); a first kClocked scheduler test (feed a regular clock in kClocked mode, assert grains land on clock edges and the first division after a mode switch is correct) — this also closes part of the "no kClocked tests" coverage gap.

## 3. MF-20 stale-voice reset + Loooop seam fractional wrap

a. **MF-20** (`src/mf20/engine.hpp`): `EnginePool::setVoices(n)` must reset engines in `[activeVoices, n)` when the count grows, so a voice that rang at high resonance and went inactive doesn't re-emit old state. `setVoices` is called every sample — the reset must only fire on growth. Header-level; unit-testable (ring voice 2, drop to 1 voice, grow back to 3, assert voices 1–2 start from silence).

b. **Loooop** (`LoopEngine.cpp`, `readInterpolated`): with crossfade off and a fractional `winStart`, the pre-wrap read interpolates toward `buf[floor(winStart)]` instead of the fractional window start (up to half a sample of error → residual click on seam-exact windowed sub-loops). Fix: when `i1` wraps, compute the wrap target by interpolating the buffer at fractional `winStart` (two reads + lerp) instead of truncating. Behavior change is confined to the wrap sample with crossfade off; existing seam tests must stay green, plus a new test with a deliberately fractional window (e.g. size such that winStart = x.5) asserting the wrap read matches the mathematically expected lerp.

## 5. Batch the Particules VCV path

Today `kWrapperBlockSize` is 1 on VCV and 64 on MetaModule. Every VCV sample pays a full `updateSlowParams()` (\~12 `getVoltage()` calls + 4 conditioner steps), a whole-struct `SetParameters()`, and per-call engine setup — the biggest remaining CPU item.

**Decision: use 64 on both hosts** (delete the `#ifdef`). Rationale: CPU amortization at 64 is maximal; the CV-conditioner decimation/smoothing constants derive from the block size, so matching MetaModule makes the two hosts' control behavior *identical* (the strongest form of "narrows VCV/MM divergence"), and it leaves a single tested configuration. Cost: 64 samples of I/O latency on VCV (1.3 ms at 48 kHz) — imperceptible for a granular texture processor, and MM users already have it.

Consequences to handle:

- `particules_cv_conditioning.h`: `CvDecimationForBlock` computes `8 / block_size` — 0 at 64 today? Read the actual function and the MM values in use; whatever MM currently computes for 64 is the target behavior for VCV too. Add the ≥1 guard (`std::max<int>(1, …)` or equivalent) while touching it — this closes the open UB-at-0 nit.
- Per-sample behaviors must stay per-sample (they already run outside the block gate): FREEZE/SEED Schmitt processing, seed-gate latch, quality-button edge detection, output reads, grain-trigger pulse output.
- Freeze/param response granularity on VCV becomes once per 64 samples (as on MM) — sanctioned behavior change.
- The round-1 "exact smoothing passthrough at block size 1" property becomes unused (block 1 no longer occurs); its tests keep passing (they test the primitive, not the wrapper) — leave them.
- Tests: extend the block-runtime/conditioning tests to pin the wrapper block size = 64 expectations if any test hardcoded 1 for VCV semantics (check `tests/particules/test_cv_conditioning.cpp` and `tests/beads/test_control_conditioning.cpp` / `test_particules_block_runtime.cpp`).

**Verification beyond the lanes:** the headless VCV-vs-expected comparisons in the beads suite already cover block-size independence (256 vs 4×64 bit-identical). A listening sanity check lands on the USER CHECKS list (dry/wet passthrough at DRY/WET=0 still instant-feeling; freeze button response acceptable).
